# Заметки переноса

## Осознанные изменения (закрытый список §14 спецификации)

1. В тексте аварийного алерта — верная команда `journalctl -u 'ai-dev@*' -n 200
   --no-pager -q`. Юнита `ai-dev.service` не существует (юниты шаблонные), и
   диагностика каждый раз начиналась с ложного тупика.
2. Отмена по SIGTERM с доведением уборки до конца вместо гонки с
   `TimeoutStartSec`: ожидания CI и агента идут под `tokio::select!` вместе с
   сигналом, задача уходит в `needs-human`, а не возвращается в очередь.
3. `ai-dev config check` как отдельная проверка, включая контракт C9.
4. Вместо `$LINENO` — человекочитаемая цепочка `.context()`: «ожидание CI, PR
   #315» → «`gh pr checks` завершился с кодом 2».
5. `--dry-run` и `--issue N` для ручной диагностики: bash умел только «взять
   голову очереди».
6. `.ai-logs/state-<issue>.json` — машиночитаемое состояние итерации, отсюда
   `ai-dev status`.

## Что найдено в bash во время переноса

Ни одно из этого не является изменением поведения «ради красоты» — это баги,
которые порт был обязан либо воспроизвести, либо починить. Починено:

* **`REWORK_WHY` присваивалась, но никогда не читалась.** Три разных исхода
  ревью — «остались `REQUEST_CHANGES` после всех кругов», «агент не доработал
  PR», «после доработки CI покраснел» — приходили человеку одним и тем же
  текстом «⚠️ Авто-ревью запросило правки». Причина возвращена в комментарий
  (`prompts::msg::review_request_changes`) и в `HumanReason::ReviewRequestChanges`.
* **Лог упавшего CI не доезжал до агента в режиме `github-app`.** `gh run list
  --branch ai/issue-N` не находил ни одного run'а, потому что в этом режиме
  ветку выбирает `@claude`, а не оркестратор; агент получал строку «(не удалось
  скачать лог CI)» вместо лога. Теперь ветка берётся у самого PR
  (`gh pr view --json headRefName`) с откатом на `ai/issue-N`.
* **`queue_size` в смотрителе бэклога всегда возвращал 0 при двух доверенных
  авторах.** GitHub складывает несколько `author:` в одном запросе по И, а не
  по ИЛИ — на этом сервере `ALLOWED_AUTHORS=jack5505 app/claude`. Смотритель
  считал очередь пустой и каждую неделю заводил новые задачи поверх затора.
  Здесь очередь считается одним общим кодом (`queue::fetch`, контракт C1):
  запрос по каждому автору отдельно, объединение, сортировка от старых.
  Строка запроса, которая уходит в промпт агента, оставлена дословно как в bash
  — правка формулировок промптов в перенос не входит (§10).

Найдено сухим прогоном на боевых данных уже после первого коммита:

* **`gh issue view N --json body,comments` не возвращает поле `number`.**
  Пока `Issue::number` был обязательным полем, разбор ответа падал на каждой
  задаче, и проход разблокировки (C6) молча не видел ни одной из четырёх
  заблокированных задач android. Поле получило `#[serde(default)]`, а на
  формат ответа есть регрессионный тест (`gh::model::tests`).

## Отличия реализации от буквы спецификации

Все — технические, на поведение не влияют:

| В спецификации | Здесь | Почему |
| --- | --- | --- |
| `envy` + `serde` для конфига | свой разбор `KEY=value` | `envy` читает только `std::env`, а конфиг инстанса нужно грузить из файла; `std::env::set_var` в новых редакциях unsafe |
| `fs4` для `flock` | `libc::flock` напрямую | тот же системный вызов, что у bash (`flock -n 9`), — замок общий у bash и Rust, это обязательное условие недели «в тени» |
| `time` для дат | `chrono` | сервер живёт в CEST, а не UTC; `time` отказывается отдавать локальное смещение в многопоточной программе, из-за чего формат лога `[%F %T]` уехал бы на два часа |
| четыре трейта внешнего мира | пятый — `git::Vcs` | иначе сценарные тесты требовали бы настоящего клона с настоящим origin, а в сборочном образе git отсутствует |
| `cargo build --release` на сервере | сборка в контейнере (`build.sh`) | на сервере нет линковщика `cc` и прав на `apt`; результат — статический musl-бинарник |

Дополнительно: спецификация снята с версии скрипта от 2026-09-19 (739 строк), а
источником переноса была установленная версия (802 строки). В ней есть проход
`sweep_stuck_merges`, которого в спецификации нет, — он перенесён целиком
(`orchestrator::sweep`): PR, поставленный на авто-merge и позже
конфликтнувший с базой, иначе висит вечно, потому что метка очереди с задачи
уже снята.

## Проверенный паритет

* `ai-dev queue` против bash-запроса на обоих боевых инстансах (2026-09-22):
  `backend` — 0 задач и там, и там; `android` — одна и та же задача #309.
* Замок: `ai-dev run --dry-run --instance android` во время работающей
  bash-итерации корректно вышел с «Другой запуск ещё работает» и кодом 0 —
  `flock` общий у обеих реализаций.
* `ai-dev doctor` на сервере нашёл оба инстанса, оба пользовательских таймера и
  подтвердил запас C9 (`APP_WAIT_MIN=180` мин против `TimeoutStartSec=4h`).
* Проход разблокировки на боевых данных android: четыре задачи с меткой
  `blocked` разобраны, у всех найден маркер `BLOCKED-BY`, блокеры открыты —
  ни одного действия, как и у bash. Ложных срабатываний C6 нет.
* Сводка сторожа PR совпадает с фактическим состоянием репозиториев
  (10 открытых AI-PR на android, 6 на backend).
