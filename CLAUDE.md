# Правила работы в этом репозитории

Это перенос боевого оркестратора `ai-dev` (bash → Rust). Спецификация
поведения и список контрактов — в [PORT-NOTES.md](PORT-NOTES.md) и README.

## Сборка и тесты

На машине разработки может не быть линковщика, поэтому сборка идёт в контейнере:

```sh
./build.sh          # cargo build
./build.sh test     # cargo test — обязательно перед каждым коммитом
./build.sh clippy   # clippy -D warnings
```

Если в системе есть `cc`, работают и обычные `cargo build` / `cargo test`.

## Что нельзя менять без отдельного обоснования

* **Контракты C1–C11.** Каждый оплачен инцидентом; список и цена ошибки — в
  README и PORT-NOTES. Трогать их можно только вместе с тестом, который
  доказывает, что поведение не потерялось.
* **Тексты промптов** в `src/prompts.rs` — перенесены из bash дословно. Правка
  формулировок и перенос — разные коммиты: иначе непонятно, что именно
  изменило поведение агента.
* **Формат лога** `[%F %T] сообщение` — по нему написаны рецепты grep к
  journalctl.
* **Коды возврата**: 0 — штатное завершение (включая «очередь пуста», «замок
  занят», «ушло человеку»), 1 — авария, 2 — ошибка конфигурации.

## Как устроен код

Внешние миры за трейтами: `gh::GitHub`, `agent::Agent`, `notify::Notifier`,
`clock::Clock`, `git::Vcs`. Отсюда тесты без сети и `--dry-run` как
декорирующая реализация (`gh::dry`), а не `if` по всему коду. Исход итерации —
`orchestrator::Outcome`; у каждого варианта ровно один хендлер, тексты для
людей живут в `prompts::msg`.

Новое изменяющее действие обязано:
1. появиться в трейте (а не вызываться `Command`-ом из середины логики);
2. получить строку в `gh::dry` — иначе `--dry-run` соврёт;
3. быть покрытым сценарным тестом в `tests/scenarios.rs`.
